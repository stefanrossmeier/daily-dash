# Git-backed Data Persistence

## Purpose

DailyDash initially stores collected runtime data in the private
`daily-dash-data` Git repository.

Git is used during this phase because it provides:

- easy inspection;
- readable data artifacts;
- version history;
- diffs;
- reproducible evaluation data.

Git is not intended to be the permanent production database.

DailyDash storage boundaries are designed so this backend can later be
replaced by a database or object storage.

## Repository separation

The public repository contains application and orchestration code:

    daily-dash

Collected runtime data lives in the private repository:

    daily-dash-data

The intended VPS checkout layout is:

    /var/code/daily-dash
    /var/code/daily-dash-data

Inside the dedicated Windmill worker the stable data path is:

    /data/daily-dash-data

Host filesystem layout therefore does not leak into application or workflow
logic.

## Authentication

Automated Git persistence uses a GitHub deploy key scoped to the private
`daily-dash-data` repository.

The deploy key has write permission only to that repository.

Its private key is stored as the Windmill secret:

    f/daily_dash/data_repo_deploy_key

The private key must never be committed to Git.

## Generic persistence script

The reusable Windmill script is:

    f/daily_dash/persist_data_repo

It is intentionally independent of Markets, News, ranking and LLM logic.

Its inputs describe:

- deploy key;
- data repository path;
- relative subtree to persist;
- remote URL;
- branch;
- commit message.

## Safety behavior

The persistence script:

- stages only the requested relative subtree;
- refuses invalid relative paths;
- refuses pre-existing staged changes;
- serializes persistence operations using a repository-local lock;
- refuses unexpected remote divergence;
- never performs an automatic merge or rebase;
- uses strict SSH host-key verification;
- creates a commit only when changes exist;
- can push an already-created local commit after a previous push failure;
- succeeds without creating a commit when there are no changes.

The last two properties make the operation suitable for Windmill retries.

## Markets flow

The Markets flow is stored using the filesystem convention generated by the
pinned Windmill CLI:

    f/daily_dash/markets__flow/flow.yaml

Its remote Windmill path is:

    f/daily_dash/markets

The flow is:

    Run Markets
        |
        v
    Persist generated data

`run_markets`:

- retrieves market data;
- processes the snapshot;
- writes JSON into `markets/snapshots`;
- renders the report;
- sends the Telegram message.

`persist_data_repo` then:

- stages `markets/snapshots`;
- creates a data commit if needed;
- pushes the resulting revision to the private repository.

The persistence step runs only after the pipeline step succeeds.

## News reuse

News will use the same persistence mechanism.

Conceptually:

    Retrieve / rank / select
        |
        v
    Write immutable run artifact
        |
        v
    persist_data_repo
        |
        v
    Deliver Telegram report

The persisted run artifact contains the complete normalized retrieval result,
the ranked candidate set and the final selected IDs. The data repository is a
write-only output sink: News scheduling, retrieval, ranking and selection do not
read prior artifacts as workflow state.

The News flow provides a profile-specific `data_path` and commit message, but no
new Git persistence implementation is required.

This keeps storage mechanics independent from ranking and model behavior.

## Future migration

When Git-backed persistence is replaced by PostgreSQL, object storage, or
another backend, retrieval, ranking, LLM processing and presentation should
not depend on that change.
